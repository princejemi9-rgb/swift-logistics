# Supabase migration

Migration order: `schema.sql`, `002_auth_profile_and_public_tracking.sql`, `003_operations_location_fields.sql`, `004_atomic_shipment_booking.sql`, then `005_idempotent_shipment_booking.sql`. Existing deployments should apply only unapplied migrations, using the trusted migration/table owner. Do not rewrite previously applied files.

The Supabase adapter is `api/index.js`; `server.js` is the separate local SQLite runtime. Never expose a service-role key in browser code. Booking uses the authenticated user's token, not a service-role key.

Migration 004 adds `create_shipment(jsonb)`: it derives ownership from `auth.uid()`, validates input, and creates the shipment and its initial event in one function call. Migration 005 replaces the customer-facing path with `book_shipment(uuid,jsonb)`. It derives ownership from `auth.uid()`, canonicalizes supported request fields, records the owner/key/request JSONB in `booking_requests`, and uses the `(owner_id, idempotency_key)` primary key as the database concurrency claim. The same owner/key with the same payload returns the originally persisted shipment and initial event with `replayed: true`; a changed payload raises `PT409`; a different key creates a separate shipment. The old RPC is not executable by customer roles, and customers receive no direct event-write permission.

The browser sends a UUID `Idempotency-Key` for each logical booking. It persists only the owner/key in session storage before sending. On a timeout or network interruption it retains that key and tells the customer to check history before retrying unchanged details. On a confirmed success or form reset it clears the key; a genuinely new booking creates another key. The API maps: missing/malformed key `400`, validation failure `422`, missing/expired identity `401`, permission denial `403`, payload mismatch `409`, and unknown database failure `503`. Both new and replayed successful responses use `201`; `Idempotency-Replayed` is `false` or `true`.

Before any future release, apply all migrations to a **fresh disposable local Supabase database**, then run `tests/booking-rls.sql` as its migration owner with `psql -X -v ON_ERROR_STOP=1 -v allow_local_booking_tests=1 -f tests/booking-rls.sql`. This test refuses non-loopback TCP connections/nonempty application data, covers replay/mismatch/owner isolation/direct-write denial, and rolls back fixtures. For a true simultaneous-request check, use two authenticated sessions with the same owner/key and confirm only one shipment/event exists and one response is replayed. Never run it against production. No isolated database runtime was available during implementation, so SQL execution and RLS/rollback assertions remain unverified.

Coordinate migration 005 and the new API during a future reviewed maintenance/release window: all customer booking calls must use `book_shipment`, and PostgREST must discover that function before booking is reopened. Verify actual policies/grants for drift and customer/staff/public behavior in staging. No migration has been applied remotely and nothing has been deployed by this task.
